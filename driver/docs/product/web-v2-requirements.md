# Web v2 产品需求规格

## 1. 文档地位与读取规则

本文是“智能停车优化与调度系统”Web v2 的当前有效产品需求来源。后续 Codex 对话在规划或
实施 Web v2 前，必须先读取：

1. `AGENTS.md`；
2. `WEB_V2_STATUS.md`；
3. 本文；
4. `docs/product/web-v2-decision-log.md`；
5. `docs/product/web-v2-implementation-blueprint.md`；
6. `WEB_V2_STATUS.md` 指向的当前 ExecPlan（若不为 `null`）。

本文只记录产品需求，不表示已经授权实施。当前状态是：**M1–M3 已批准；M4 R0a–R5 已验收，
R6.1及路径展示改进已完成，M4待用户验收；跨站实际接入及M5界面未实施**。是否可以实施以
`WEB_V2_STATUS.md` 为准，不得因为本文已记录或已有实现而自动开始下一恢复点。

如本文与聊天记录摘要冲突，以本文当前版本为准。旧项目阶段和界面规则不自动适用于 Web v2；
如需复用或改变 v1 算法、研究证据或 Schema，则按 `AGENTS.md` 的隔离规则处理。

## 2. 产品定位

### 2.1 目标

Web v2 首先是面向普通车主的高质量商业化停车产品原型，同时提供完整的大创结项答辩模式。
核心用户流程为：

```text
搜索停车场
→ 查看模拟实时空位
→ 选择入口和停车需求
→ 获得推荐车位
→ 确认纵深协同停车风险（如适用）
→ 临时预留
→ 场内路线指引
→ 动态重规划
→ 确认停车完成
```

### 2.2 当前真实性边界

- 第一版使用明确标记的 synthetic 数据；
- 暂无真实停车场时序、车位传感器或管理系统 API；
- 保留真实停车场数据输入、校验和适配接口；
- 第一版可实际公网部署，但不等于已投入真实商业运营；
- 不得宣称实时空位来自真实停车场，不得宣称具备自动驾驶控制能力；
- 正式 v2 公平实验完成前，不得宣称新版算法性能优于 v1 或其他算法。

### 2.3 产品名称

继续使用“智能停车优化与调度系统”，不另造商业品牌名称。答辩模式可同时显示完整科研项目
名称“智能停车场车位分配与纵深移位优化”。

## 3. 双模式信息架构

网站默认进入车主模式。电脑端顶部导航右侧提供“答辩模式”开关；手机端放入顶部菜单。
公网答辩模式需要演示级访问口令，本地离线版不依赖公网。

### 3.1 车主模式

一级页面只保留三个：

```text
找停车场
智能停车
当前行程
```

#### 找停车场

- 按停车场名称和区域关键词搜索；
- 使用美化后的区域坐标示意图，不接真实地图、不绘制虚构道路；
- 示意图包含柔和背景、区域标签、模拟用户位置、停车场标记和联动详情；
- 支持选择模拟区域，也支持在示意图上点击更新模拟位置；
- 电脑端采用位置图、列表与右侧详情面板联动；
- 手机端采用全屏位置图、底部抽屉或全屏详情；
- 两端功能完整一致；
- 首屏最多显示三项与停车选择直接相关的概览：附近停车场数量、合计可用车位、最近距离；
- 停车场卡片显示模拟实时空位、距离、预计到达时间、营业状态、开放时间、参考小时价格、
  空位更新时间和充电位概况；
- 停车场距离和预计到达时间来自版本化 synthetic 场景字段，只表示场外摘要，不绘制或暗示
  真实道路导航；场内路线从停车场入口开始单独计算；
- 第一版不提供按距离、价格、空位筛选或排序，留作后续版本。

#### 智能停车

- 用户选择入口；
- 默认普通停车，可附加“需要充电”硬条件；
- 第一版不提供无障碍车位需求；
- 当前车主模式实际调用已验证的 `OnlineRuleServiceV2`，统一显示为“智能推荐”；未来研究算法发布到
  车主端的要求见第 18 节，未通过发布校验/启用前保持现有默认；
- 车主模式隐藏算法名称，只显示“智能推荐”、通俗理由和至多一个合规备选；
- 主推荐可以是普通独立位或纵深协同停车位；
- 充电需求必须由后端进入候选过滤和结果校验，不能只做前端标签；
- 无可用充电位时，用户可保持需求进入等待，或主动取消需求后重新推荐；
- 不得静默把充电需求降级为普通车位。

#### 当前行程

- 展示当前停车场、推荐/预留车位和剩余预留时间；
- 高亮入口到目标车位的管理层路线；
- 展示距离、预计行驶时间和分步骤文字指引；
- 展示当前用户车辆连续移动，并显示少量相关周边车辆；
- 提供可控的“模拟偏航”和“模拟车位被占”；
- 偏航后重新计算到原目标的路线；
- 车位被占后释放原推荐、重新推荐并生成新路线；
- 到达后由用户选择“已停入”或“无法停入”；
- 动画结束不能自动修改车辆真实状态；
- “已停入”将会话预留转为占用并更新空位；
- “无法停入”记录原因，释放或标记原位异常，再推荐其他车位；
- 停车完成后显示停车场、区域、车位编号、停车开始时间、查看停车位置和结束演示；
- 保留当前会话内的简短停车记录，不建立账户级长期历史。
- 始终显示完整停车场二维俯视布局，而不是仅显示抽象路线骨架；布局包含全部车位、占用车辆、
  入口/出口、分区、主通道及方向、充电区、纵深组、专用缓冲位和不可通行区域；
- 当前车辆、目标车位和路线叠加在完整布局上。车辆位置是基于同一服务端 `Route` 的 UI 插值，
  不是实时定位；支持缩放、拖动以及聚焦车辆/目标车位；
- 关闭页面或离开结果页不自动释放占用；“结束并重置演示”才释放 synthetic 占用，并把记录
  标记为“演示已重置”。正常离场事件则把占用转为 `DEPARTED`；记录状态和空位状态必须一致。

### 3.2 答辩模式

电脑端使用可折叠左侧导航，仿真页面可收起导航扩大画布；手机端使用顶部菜单或抽屉。

```text
项目总览
布局与状态
算法对比
交互仿真
纵深停车专题
研究证据
数据与扩展
```

#### 项目总览

用于答辩开场，说明现实问题、系统边界、当前成果、可运行算法、数据真实性、网站能力、核心指标、
最近一次对比摘要、已验证内容和不能外推的结论。页面控制在约一屏至一屏半，详细公式放文档。

#### 布局与状态

复用与车主端相同的完整布局画布，但使用独立答辩路由 `/defense/layouts/:parkingLotId`。支持布局/
状态/需求导入、校验、叠图确认、草稿发布、场景副本、画布编辑和表格批量编辑；编辑能力不得进入
车主路由或打包为仅隐藏的按钮。

#### 算法对比

页面包含两个清晰分离的标签页：

```text
单次交互对比
批量评估
```

两者使用统一算法接口，但指标、结论和导出分开。单次对比并排显示推荐车位、路线、解释、原始指标
与 Pareto 关系；批量评估运行冻结事件和随机种子，生成长期指标、失败记录与敏感性分析。

#### 交互仿真

引导演示至少覆盖：新车入场、纵深受阻离场、无可行车位与等待、偏航重规划、推荐位被占。
自由实验保留并增强现有交互式停车沙盒，支持选择布局、添加车辆、入场/离场、开关车位、
候选解释、阻挡和移位、失败降级、重置及导出。

算法选择器规则：

- 在线规则：M2 后由 `OnlineRuleServiceV2` 实际运行，并清楚标注“复用 v1 可行性与纵深恢复
  能力”；不得把它命名为“在线规则 v1”或展示为 v1 正式实验运行；
- 最近可行基线 `nearest_feasible_v1` 和随机可行基线 `random_feasible_v1` 可在 M5 答辩命名空间
  接入；只有通过统一输入输出、硬约束、路线、公平性和固定种子复现测试后才标记为可运行实验基线；
- 车主模式不得选择或调用两个实验基线；
- 模拟退火等未实现分配算法：置灰并标记“待接入”；
- 随机森林：归入预测模块，置灰并标记“待接入”；
- 待接入项目可查看定位、需要的数据和接入条件；
- 未实现算法绝不能产生伪造结果。

#### 纵深停车专题

独立突出项目特色，完整展示：车辆进入纵深位、阻挡形成、深位车辆请求离场、浅位车辆移入
缓冲位、目标离场、浅位车辆恢复原位。上层使用通俗动画，下层展示 `depth`、缓冲映射、
执行资源、事务锁、失败关闭和恢复顺序。

#### 研究证据

- 区分已验证工程能力、synthetic 案例现象和仍待验证事项；
- 展示核心指标、单次决策解释、完整审计和失败案例；
- 当前仿真指标与保存的正式实验结果分开展示；
- 默认快捷指标为车辆数、空位、等待车辆、移位次数和决策耗时；
- 可展开吞吐量、利用率、等待、移位距离和资源利用率；
- 所有案例数字必须标记证据等级，避免被误认为真实场地结论。

#### 数据与扩展

集中展示 synthetic 数据来源、真实停车场接口、字段映射、隐私、更新时间、接口健康状态、
未来前后端架构、算法接入规范和路线图。第一版不将自由实验台包装成运营管理后台。

M5 按以下接口和生命周期实施，不得提前塞入 M4 车主路由：

- 布局 JSON、状态 CSV/JSON 和需求事件 CSV/JSON 分离；状态文件允许部分覆盖，缺失车位统一为
  `unknown` 并排除所有推荐；
- 布局导入使用“草稿 → 自动校验 → 原图叠图人工确认 → 已校验 → 人工发布”。只有已发布版本
  才能进入车主搜索、推荐和路线；关键错误失败关闭，非关键警告显式展示；
- 原图只用于答辩叠图校验，车主页面只显示标准化矢量布局。发布布局原子保存到环境变量指定的
  本地受管数据目录，记录版本、哈希和发布清单，不写入 Git；
- 答辩状态编辑作用于独立会话副本，支持画布单个编辑、表格筛选/多选批量编辑、CSV 差异预览、
  撤销/重做、保存和导出；服务重启后恢复默认，可用导出 JSON 重新导入；
- 编辑导致已推荐/预留/导航目标失效时，服务端原子终止旧 attempt，记录原因，并创建替代推荐或
  `WAITING`，页面只恢复权威状态；
- 答辩模式提供单次交互对比和批量评估两个标签页。内置四套版本化固定事件集，并允许上传经校验
  的需求文件；在线算法不得提前读取未来离场真值；
- 单次对比使用同一布局、状态、需求、可见信息和预算运行在线规则、最近可行及随机可行基线；随机
  单次使用显式种子，批量报告使用冻结的 30 个种子并保留每次结果；
- 默认先做硬约束门禁，再用 Pareto 逐项比较，不提供官方万能总分。用户可在 ETA 与预计移位总耗时
  两个独立维度间调整百分比权重；固定参考上下限归一化，算法耗时作为门槛/平局项；
- 预计移位总耗时为每次固定操作耗时加缓冲路线行驶时间之和；固定操作参数优先复用并核验 M3
  版本化参数。移位次数和距离展示但不重复计分；
- 报告必须包含原始指标、可行/失败/降级、布局/状态/需求/算法版本、参数、种子、预算、权重和
  敏感性分析；单次结论与需求满足率、吞吐量、时空利用率、累计移位等批量指标分开。

### 3.3 双模式状态隔离

- 两种模式都空闲时可共享“最近浏览停车场”作为进入时默认值；任一模式出现等待、软锁、预留、
  导航、占用或实验修改后，各自固定停车场和布局版本，直到该模式正常结束或显式重置；
- 车主推荐、软锁、预留、导航和停车记录与答辩实验状态彼此隔离；
- 可共享内容仅限空闲时的默认停车场 ID 和基础不可变布局版本；车主和答辩各自拥有独立的可变
  场景副本。答辩修改布局时创建仅属于 defense 命名空间的派生布局版本；
- 每个匿名浏览器会话拥有独立 synthetic 场景，公网访客之间不共享软锁、预留、占用或实验修改；
- 切换停车场时，`SOFT_HELD`、`SESSION_RESERVED` 或 `NAVIGATING` 状态必须先确认取消，成功
  释放原声明并清除导航后才能切换；`OCCUPIED` 状态禁止直接切换，必须先正常离场或执行明确
  的“结束并重置演示”；
- 一个车主会话只能有一个有效预留或行程；
- 从车主模式切换到答辩模式不会暂停、延长或取消车主状态；业务倒计时继续，返回时按服务端
  权威状态恢复。界面在切换前提示存在活动车主行程；
- 车主模式只有正常离场、显式“结束并重置演示”或带审计的会话垃圾回收才能释放 synthetic
  占用；普通页面跳转、关闭结果页或模式切换不得释放；
- 答辩模式可在自身场景副本中选择保留占用或重置，以支持连续多车和纵深阻挡演示。
- synthetic 会话过期回收时，软锁和预留按既有期限释放；仍处于 `OCCUPIED` 的资源以
  `DEMO_SESSION_GC` 原因释放并保留审计。M3 冻结车主命名空间闲置 TTL 为 30 分钟、答辩
  命名空间闲置 TTL 为 2 小时；软锁 30 秒和预留期限独立计算，不因会话访问而延长。页面必须
  提示演示状态不会跨设备或无限期保存。

## 4. 四个 synthetic 停车场

第一版提供四个通用场景，名称保持简洁，页面统一标注“模拟实时数据”：

| 停车场 | 主要特色 |
|---|---|
| 商场停车场 | 普通车位为主、参考价格较高、空位相对较少 |
| 学校停车场 | 混合纵深布局，重点展示阻挡、缓冲位和被动移位 |
| 医院停车场 | 多入口和较复杂的管理层路线 |
| 交通枢纽停车场 | 规模较大并包含充电车位 |

四个停车场都必须支持详情、空位更新、推荐、预留、导航、异常处理和停车确认，不允许只展示
卡片但无法进入完整流程。停车费采用不同的简单小时参考价，不实现复杂计费和支付。

### 4.1 M4 完整布局修订

M4 原车主流程保留，但当前抽象路线骨架未达到布局验收要求，M4 在进入 M5 前重新打开并完成以下
基础层：

- 保留现有公开停车场 ID、名称和 URL；新增四套默认大布局，旧小布局改为显式 legacy 回归场景；
- 容量固定为商场 48、学校 28、医院 32、交通枢纽 52，共 160 个停车用途物理车位；专用缓冲位
  不计入容量，也不得被推荐；当下可推荐集合由状态、声明、硬约束和可达性共同决定；
- 充电位分别为 8、4、6、10；学校配置 4 组两层纵深位，其他停车场各 1 组；这些数量表示物理
  类型配置，不表示默认空闲数量；每组由
  `stack_group_id` 和连续 `depth` 表示。首批纵深位与充电位不重叠；
- 学校提供 2 个专用缓冲位，其他停车场各 1 个；缓冲位、路网和纵深恢复路线必须显式可达；
- 商场和交通枢纽以单向环流为主；学校和医院采用双向主通道加局部单向停车排。道路方向属于
  路由硬约束，禁止逆行；
- 商场、医院和交通枢纽提供多个入口或出口，学校使用单入口/单出口；入口由服务端上下文提供；
- 首批均为单层，完整布局契约从第一版支持楼层和显式跨层连接，不为未来多层重新破坏契约；
- 默认状态快照完整覆盖全部车位，约占用率分别为 65%、50%、70%、60%，可包含少量有明确原因的

### 4.3 M4 R5 车主 synthetic 演示情景轮换

## 5. 推荐、纵深和等待规则

### 5.1 在线规则 v2 服务

- 当前车主命名空间唯一可用算法注册项为 `OnlineRuleServiceV2`（后端 ID `online-rule-v2`），车主
  界面统一称“智能推荐”；M5 答辩界面才称“在线规则”，实验基线按 3.2 节独立注册，不改变车主
  选择；
- 它复用 v1 `OnlineRulePolicy` 的已验证可行性、纵深恢复和确定性候选解释，但不是原始 v1
  正式实验结果；
- v2 服务先校验停车场作用域、会话和硬条件格式，把当前物理占用、关闭、异常以及所有有效 v2
  软锁/预留投影到 v1 `observed_snapshot`，同时保持完整 v1 布局结构不删车位；再取得只读候选
  可行性与纵深恢复解释，之后应用充电、营业和动态可达等 v2 新候选过滤，最后按给定路径成本
  快照完成合法排序并复核结果；不得通过删除非充电位后再运行 v1 来扭曲容量和恢复判断；所有
  投影、新增过滤、排序和降级均进入审计记录；
- 不修改 v1 Schema、算法文件、历史哈希或正式实验产物；
- 车主模式固定采用 `strict_recoverable`；
- `risk_accepting` 只在答辩模式作为研究策略展示，默认不启用；
- M2 的 v2 服务对给定的版本化路径成本快照完成推荐排序；M3 的事件引擎根据通道占用生成新
  成本快照并触发预计时间更新和重规划；
- 充电属于 v2 硬约束；距离、阻挡、容量和路径使用明确的词典序与确定性平局规则，具体字段
  和顺序在 M2 契约中冻结；
- 车主推荐还必须满足“当前路线预计到达时间 + M3 冻结的 60 秒安全余量 ≤ 五分钟预留窗口”；不满足
  时该车位不能作为可完成的主推荐。答辩研究场景可展示不可行案例，但必须标记失败原因；
- 车主端只显示主推荐、一句通俗理由和至多一个合规备选；
- 答辩端显示完整候选、排序依据、耗时和求解状态；
- 普通用户不能调整未经验证的目标权重。
- 备选必须满足与主推荐完全相同的硬条件；没有合规备选时显示“暂无备选”并提供等待或修改
  需求，不得用普通非充电位替代充电需求。

### 5.2 纵深位知情确认

现有纵深车位与被动移位规则必须保留。车主模式中，纵深位只有在严格可恢复校验通过时才能
推荐；存在满足相同硬条件的普通位时同时给出普通位备选，否则明确显示暂无合规备选。用户必须
在确认停车前明确接受“协同停车位可能需要临时移位”，
拒绝后排除该纵深候选并重新推荐。车主端使用通俗术语，答辩端展示完整技术语义。

### 5.3 软锁与会话预留

Web v2 的应用层状态为：

```text
IDLE
→ WAITING（无合规车位时）
→ SOFT_HELD（服务端推荐并原子声明，30 秒）
→ SESSION_RESERVED（用户确认后，产品逻辑默认 5 分钟）
→ NAVIGATING
→ OCCUPIED
→ DEPARTED

任意未完成阶段可按合法转换进入 CANCELLED / EXPIRED / FAILED
```

`RECOMMENDED` 不是持久业务状态，只是服务端计算中的瞬时结果；只有服务端为主推荐原子创建
排他声明后，才向前端返回 `SOFT_HELD`。纵深风险确认发生在 30 秒软锁期间，接受后进入
`SESSION_RESERVED`，拒绝或
超时立即释放；普通位也在软锁期间确认。重复确认、取消、过期清理和重试都必须幂等，资源
所有者由会话 ID、场景 ID 和停车场 ID 共同限定。
`WAITING` 不声明具体车位。旧推荐尝试以 `FAILED` 或 `EXPIRED` 结束后，重新推荐会创建一个新的
attempt ID；不得把已终止 attempt 直接改回活动状态。

- 30 秒内未确认或用户拒绝，立即释放软锁；
- 当前会话中的其他模拟车辆不能获得已软锁车位；
- 答辩演示可将确认后的 5 分钟预留加速为 60 秒；
- 用户主动取消或预留超时后释放，并提示重新推荐；
- 这些应用状态不得与现有移位事务容量预留混用；
- 所有预留只影响当前 synthetic 会话，不写入正式 v1 实验产物。
- 30 秒和车主模式 5 分钟使用 FastAPI 服务端权威计时：单进程内用单调时钟计算持续时间，
  API 同时返回 UTC 到期时间用于显示；前端倒计时没有续期权，刷新或断线不能延长期限；若
  后续使用共享会话存储，则由存储 TTL 和原子操作负责跨进程期限；
- 答辩模式可在独立实验场景中把 5 分钟映射为 60 秒，但不得改变车主状态，也不得把仿真倍速
  应用于安全相关墙钟；
- “模拟车位被占”定义为外部物理观测覆盖应用预留，而不是系统重复分配：记录冲突事件，原
  预留进入 `FAILED`，释放应用声明后重新推荐；
- “结束并重置演示”是测试控制命令，不是业务状态；它释放场景资源并保留带 `DEMO_RESET`
  终止原因的会话记录。
- 主推荐在返回前被软锁，备选只作为当时合规快照而不预锁；用户选择备选时，服务端必须原子
  尝试锁定备选，成功后再释放原主位。备选已不可用时保留仍有效的原锁或要求重新推荐，不得
  同时持有两个车位声明。
- 五分钟期限从进入 `SESSION_RESERVED` 时开始，进入 `NAVIGATING` 不续期；期限内未转为
  `OCCUPIED` 则进入 `EXPIRED`、释放车位并使原路线失效。断线重连和模式切换同样不续期。
- 动态重规划后若预计到达时间加安全余量超过剩余期限，界面立即显示“可能无法在预留期内
  到达”，提供继续导航到期限结束或主动重新推荐；不得静默延长原预留。
- 同一浏览器的多个标签共享服务端匿名会话；服务端以版本号和原子命令保证一个 driver 会话
  只能有一个活动等待、软锁、预留或行程，旧标签收到冲突后刷新权威状态，不能覆盖新状态。

### 5.5 M3 性能与复现预算

M3 以单进程、本地答辩电脑和 synthetic 数据为验收环境，冻结以下开发预算；这些数字只说明
演示原型能力，不代表生产并发承诺：

- 状态机命令 p95 不超过 100 ms；
- 推荐并原子创建软锁 p95 不超过 500 ms，绝对超时仍为 3 秒；
- 动态路线重规划 p95 不超过 100 ms；
- 100 辆车、10,000 个事件的确定性仿真重放不超过 2 秒；
- 上述压力场景增量峰值内存不超过 256 MB；
- 固定种子重复运行的事件序列和最终状态哈希完全一致。

2026-10-17 用户重新确认接受仅限 M4 演示的仿真性能波动例外：本轮 pytest 2.7115064 s 未通过，
补充同负载测量 1.982145 s。原 ≤2.0 s 门、测试和失败记录保留；例外不等于性能门通过，也不构成
M3/M6 性能承诺的放宽。没有授权切换系统电源、修改算法或依赖。

### 5.4 充电位等待

没有可用充电位时显示等待状态、已等待时间、手动刷新和取消等待；不伪造队列位置或预计等待
时间。车主 synthetic 场景自己的确定性事件调度器可以释放一个充电位，车主页面检测后自动
重新推荐并进入新的 30 秒软锁；答辩模式可在独立场景副本中演示同类事件，但不得直接修改
车主等待、预留或行程状态。
只有活跃车主客户端的轮询、恢复连接或手动刷新请求才能触发从 `WAITING` 到新推荐并创建软锁；
后台事件本身不为不可见用户提前启动 30 秒倒计时。自动尝试必须限频并使用幂等键。

## 6. 导航与多车管理层仿真

### 6.1 导航

- 路网、动画和文字指引必须使用同一条后端路线；
- v2 布局为每个入口配置初始朝向，路网节点带坐标；
- 后端根据路径边长和转角阈值生成直行、左转、右转和到达指令；
- 前端不自行推导第二套路线逻辑；
- 明确标注为管理层方向提示，不是实车级导航或自动驾驶轨迹。

2026-10-17 获准修复指引显示缺口，规则在实施前冻结：方向仅相对默认二维管理层画布（x 向右、
y 向下），不是地理方位。以既有 Route 节点向量比较前后方向，绝对转角 ≤30° 为直行，30°–150°
为左/右转，≥150° 使用“按高亮路线调整方向”，不宣称道路允许实车掉头。第一段若有已发布设施
入口朝向则使用该朝向；缺失时只提示“沿高亮通道前行”，不伪造初始朝向。零长度/不可判定的段
只提供中性文字；最后一个既有边步骤附“到达目标区域”，不新增步骤或自动确认停车。原点说明、
坐标、布局/Route 字段、edge/node 序列、距离、ETA、成本版本和算法排序均不改变。停车场名称
从既有 ParkingLot GET 读取，加载/失败可见，拒绝错配，不在前端硬编码 ID 映射。

### 6.2 多车仿真

第一版实现轻量的管理层数字孪生，不直接集成或复制 ParkSim：

- 多车沿管理层路线连续移动；
- 展示进入、等待、停车、离场和移位状态；
- 通道繁忙影响等待和路径成本；
- 支持偏航和车位被占后的动态响应；
- 支持完整纵深缓冲移位动画；
- 支持播放、暂停、单步、倍速和重置；
- 同时支持确定性预设场景和自由交互；
- 不默认生成不可复现的随机事件；
- 车主模式只显示自己的车辆和少量周边车辆；
- 答辩模式显示完整车辆、事件、资源和指标；
- 二维俯视图是完整、可靠的功能基线；
- 二维模式在电脑和手机上完整可用；伪 3D 是 M5 条件增强，只有通过目标设备性能门才开放，
  未通过时不影响首版验收，也不得显示不可用开关冒充已实现；
- 不实现车辆动力学、转向控制、感知、碰撞规避或轨迹跟踪。
- 仿真状态、动画和文字指引消费同一事件日志；前端只插值显示，不自行提交停车、占用或移位
  完成事件。

## 7. 视觉与响应式设计

### 7.1 双主题

- 车主模式：固定明亮商业主题，地图/位置图优先；

### 7.2 导航结构

- 电脑车主端：顶部横向导航“找停车场 / 智能停车 / 当前行程”，右侧答辩模式开关；
- 手机车主端：底部导航，中间突出“智能停车”，两侧为“找停车场”和“当前行程”；
- 电脑答辩端：可折叠左侧导航；
- 手机答辩端：顶部菜单或抽屉；

### 7.3 素材和声音

- 使用矢量图标、CSS 图形和代码生成图形，不使用照片；

  浏览器焦点，不故意制造明显可用性缺陷。

### 8.1 第一审批门：方向板

先制作两套方向板，且都包含电脑与手机片段：

两套方向都必须遵守“车主模式明亮、答辩模式深色”的双主题边界；最终选择的是整体视觉语言，
不是取消某一模式的固定明暗主题。

每套方向板至少展示品牌栏、模式开关、停车场卡片、位置示意图、状态标签、推荐结果、30 秒

方向确定后，交付：

- `prototypes/web-v2/` 中的独立 HTML/CSS/JavaScript 可交互原型；

原型使用静态演示数据，但串联搜索、选择、推荐、纵深确认、软锁、预留、导航、异常重规划和

1. 车主首页电脑端；
2. 车主首页手机端；
3. 智能推荐和纵深位确认；
4. 30 秒软锁和正式会话预留；
5. 当前行程、文字导航和异常重规划；
6. 答辩项目总览；
7. 答辩多车仿真和纵深移位；
8. 充电等待、停车完成信息卡和会话记录。

获批前，不进入正式 React/FastAPI 开发。
M1 中的倒计时、推荐、仿真和口令均是体验原型，不冻结算法、并发、安全或数据契约语义；这些

## 9. 技术架构

### 9.1 目标结构

```text
apps/web/                    React + TypeScript + Vite
src/parking_opt/api/         FastAPI 应用接口层
src/parking_opt/             现有算法和领域模型
schemas/v1/                  冻结研究契约
schemas/v2/                  新应用契约
prototypes/web-v2/           HTML/CSS 可交互原型
docs/design/web-v2/          方向板、PNG、视觉规范和审批记录
docs/product/                产品需求与决策日志
```

- 使用单仓库管理；
- React 只负责界面和浏览器交互，不复制 Python 算法；
- FastAPI 包装只读 v1 适配能力、`OnlineRuleServiceV2`、会话、数据适配和导航服务；
- 开发期允许 Vite 与 FastAPI 分端口运行；交付期由 FastAPI 同源托管 Vite 构建产物，本地用户
  只启动一个服务且交付运行不依赖 Node.js；
- synthetic 会话通过 `SessionStore` 接口管理；首版实现单进程内存存储和原子资源锁，公网只
  允许单应用 worker。未来多实例或真实锁位必须更换为共享事务存储；
- 后续算法通过统一注册表和版本化接口接入；
- 前端组件库、CSS 方案和动画库在视觉稿批准后选择；
- 新增重要依赖前必须说明用途、许可证、体积、兼容性和替代方案；
- 现有 Streamlit 完整保留为科研审计、旧版演示和回归参考，Web v2 验收前不得删除或覆盖。

### 9.2 算法注册接口目标

所有未来分配算法至少公开：算法名称、版本、状态、所需信息、输入契约、推荐车位、路线、候选
解释、运行耗时、求解状态和降级记录。预测模块与分配算法分开注册。待接入算法只能展示说明，
不能执行。

## 10. v1 / v2 数据契约

### 10.1 版本原则

- v1 永久冻结，继续承载旧实验、哈希和验收证据；
- v2 独立新增多停车场、营业信息、参考价格、充电能力、软锁、会话预留、导航和动态车辆状态；
- v2 经版本化适配器调用现有在线规则，并由 v2 校验器复核结果；
- 新网站产生的 v2 演示数据单独保存；
- 不直接比较 v1 与 v2 结果；
- 无新的 v2 公平实验时，不宣称新版性能更优；
- 不因网站升级重跑全部历史 v1 实验；
- 修改 v2 产品语义时，先更新本文和 Web v2 决策日志，再更新 Web v2 计划与实现；如变更会
  直接改写共享的 v1 算法或历史证据，则必须显式提出共享资产变更，不得静默修改。

### 10.2 v2 最低数据能力

- 停车场作用域 ID，避免跨停车场车位、车辆、入口或事务重名；
- 停车场名称、区域、坐标、营业状态、开放时间、参考价格、更新时间和来源；
- 车位充电能力；
- 用户入口和充电需求；
- 软锁、会话预留、取消、过期和占用状态；
- 入口初始朝向、路网节点坐标和管理层动态成本；
- 导航步骤和车辆动画所需状态；
- 数据源和接口健康状态；
- 真实接口缺字段时失败关闭，不自动伪造。

真实数据适配器失败只关闭对应真实数据源；界面可以在用户明确可见的情况下切换到独立
synthetic 演示场景，但不得把 synthetic 值补入真实场景或继续显示为真实在线状态。
匿名会话隔离规则仅适用于 synthetic 演示数据；未来真实停车场接入必须读取共享现实状态，并
通过真实管理系统提供的事务接口锁位。缺少真实锁位接口时只能提供推荐，不能伪装成真实预留。

## 11. 部署、安全和兼容性

### 11.1 运行与部署

- 本地提供不依赖 Docker 的 Windows 一键启动前端和后端；
- 断网可完成全部答辩演示；
- 断网答辩的强制范围是答辩电脑本机完整运行；手机端完整功能通过公网真实设备和自动化移动
  视口验收。首版不为手机开放未加密局域网 HTTP；如后续需要断网手机联调，必须另行批准带
  本地 HTTPS 或可信反向代理的 LAN 模式；
- 另外提供 Docker 化和部署说明，但 Docker 不是本地答辩前置条件；
- 实际部署到免费托管平台提供的公网域名；
- 未经用户确认不得产生付费资源；
- 免费平台不满足稳定性时先报告，再决定是否升级；
- 车主模式公网公开；
- 答辩模式由后端口令保护；
- 不将口令、令牌或密钥写入仓库。
- 后端验证口令后签发短期、签名、HttpOnly、SameSite 会话；公网 Cookie 使用 `Secure`，本地
  回环 HTTP 仅放宽 `Secure`。所有状态修改 API 校验同源请求和会话作用域；

WebSocket 稳定时启用实时通信；免费平台不稳定时降级为 HTTP 请求/轮询和浏览器本地动画，
推荐仍由后端算法产生，界面必须显示降级状态。本地版优先启用完整能力。
M6 离线发布物必须包含已构建前端和可离线启动的后端运行环境；目标答辩电脑不需要 Node.js、
Docker 或联网下载。可采用经过实测的自包含可执行包或随包 Python 3.11 便携环境，M6 ExecPlan
在依赖确定后选择并冻结，但验收结果相同。

### 11.2 安全底线

- 公网环境强制 HTTPS；本地断网版可使用仅绑定回环地址的 HTTP，不监听外部网卡；
- FastAPI 服务端输入校验；
- 基础速率限制；
- 安全响应头；
- 日志脱敏；
- 环境变量配置口令和部署密钥；
- 第一版不实现正式账户、角色或运营权限系统。

### 11.3 浏览器

- 目标兼容 Edge、Chrome、Firefox 和 Safari；Safari 必须在真实 Safari/iPhone 上完成关键流程
  验证后才能声明通过，仅有 Playwright WebKit 结果时必须标记“Safari 实机待验证”；
- 覆盖电脑和手机；
- Edge/Chrome 作为主要视觉基线；
- Firefox/Safari 做功能和布局兼容检查，不要求逐像素一致。

## 18. 双站算法发布方向（2026-10-18 用户明确选择）

- 最终产品必须支持研究站算法发布到车主端使用；研究站不再仅是与车主隔离的离线实验工具。
  现有 Streamlit 历史资产仍只读保护，外部研究站的代码/版本/接口待组员获取并核实。
- 推荐的发布边界为服务端：研究站产出版本化算法与依赖/输入输出清单，经适配、统一契约、
  硬约束、未来信息隔离、公平性、固定种子、时间预算和失败关闭验证后才可启用。未验证算法
  保持 pending；不得让浏览器直接运行上传 Python 或把研究结果 JSON 当生产推荐。
- 车主 React 继续显示“智能推荐”并消费统一 Recommendation/Route；后端维护已验证发布版本、
  启用记录及回滚。当前实际默认仍是 online-rule-v2，本轮不提前注册未验证算法或改变排序。
- 算法只负责候选决策；软锁、会话、预留、占用、路线权威和最终可行性复核仍由 FastAPI 执行。
  失败/超时必须可见，回退策略和已启用版本可追溯，跨研究/车主命名空间不共享可变占用状态。
- 本轮改善 M4 路径演示和展示，交付组员开发对接候选包及发布/校验/启用/回滚协议建议，实际
  两站连接由组员完成。候选包如实包含性能限制，不等同正式 M4 封存、用户验收或 M6 发布。
- 验证围绕改动集中执行，保留所有失败；不重复挑最优测量，不改变已冻结阈值。性能例外仅限
  用户已确认的 M4 仿真条目，不自动扩展到 production。
