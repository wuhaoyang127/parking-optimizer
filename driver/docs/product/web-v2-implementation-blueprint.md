# Web v2 高质量实施蓝图

## 1. 文档用途

本文把已确认需求转化为可执行、可验收、可回滚的实施顺序。它不是当前 ExecPlan，也不授权
创建分支、设计稿、代码、Schema 或依赖。每个里程碑获准时，仍需根据本文建立对应 ExecPlan。

“无冲突”表示截至本次复核，权威文档之间不存在已知的范围、状态、架构、依赖或验收口径
矛盾；不表示实现没有工程风险，也不替代各里程碑的测试和用户审批。

原始产品方向来自用户逐项确认；本文中的状态机、算法适配、会话隔离、运行拓扑和里程碑重排
是为消除冲突形成的工程化消歧方案，已由用户整体接受。当前实施授权仍只读取
`WEB_V2_STATUS.md`，蓝图获批不自动授权任何恢复点。

## 2. 已冻结的总原则

1. 第一目标用户是普通车主，答辩模式是隔离的专家视图。
2. 当前是 synthetic 商业化演示原型，不冒充真实商业运营或实车导航。
3. React 不实现算法；FastAPI 和 Python 服务是业务状态与推荐结果的权威来源。
4. v1 永久只读；Web v2 通过 `OnlineRuleServiceV2` 复用能力，不冒充 v1 正式实验。
5. 二维仿真是电脑和手机的完整基线；伪 3D、声音是条件增强。
6. 每个匿名访客、车主模式和答辩模式的可变 synthetic 状态彼此隔离。
7. M1 冻结体验，M2 冻结契约，M3 冻结状态机，M6 才产生发布候选。
8. 每个里程碑必须先完成验收和恢复点，才能进入下一里程碑。

## 3. 目标架构与单向依赖

```text
React UI
  │ 只消费 v2 API、事件与视图模型
  ▼
FastAPI application layer
  ├─ session / mode isolation
  ├─ hold / reservation / occupancy state machine
  ├─ route and simulation services
  ├─ algorithm registry
  └─ data-source adapters
           │
           ▼
OnlineRuleServiceV2
  ├─ v2 scope and hard-constraint validation
  ├─ read-only v1 candidate feasibility/explanation adapter
  ├─ v2 dynamic path ordering
  └─ v2 result validation and audit
           │
           ▼
existing v1 domain and OnlineRulePolicy assets (read-only)
```

禁止反向依赖：v1 不导入 Web v2；前端不推导推荐、路线、占用或移位完成；仿真动画不直接
修改业务状态。

运行拓扑：开发期使用 Vite 开发服务器代理 FastAPI；交付构建由 FastAPI 同源托管静态前端，
浏览器只访问一个回环或公网地址。synthetic 状态经 `SessionStore` 接口访问，首版
`InMemorySessionStore` 只允许单 worker，并以停车场/场景作用域锁保证原子声明；未来可替换
共享存储而不改变 API。

## 4. 核心状态和时钟

### 4.1 场景作用域

所有可变资源使用复合键：

```text
anonymous_session_id + mode_namespace + scenario_id + parking_lot_id
```

- `mode_namespace` 为 `driver` 或 `defense`；
- 两个模式只在双方空闲时共享最近浏览停车场和基础不可变布局版本；活动后分别固定；
- 浏览器使用服务端签发的不可预测会话标识；
- Cookie 为签名、HttpOnly、SameSite；公网使用 `Secure`，本地仅回环 HTTP 可例外；修改状态的
  API 校验 Origin/CSRF 边界和复合场景作用域；
- 公网部署重启后允许 synthetic 会话重置，但必须清晰提示，不伪造持久化；
- 第一版不建立账户或跨设备同步。
- 会话闲置 TTL 在 M3 配置中冻结；回收时仍占用的 synthetic 车位以 `DEMO_SESSION_GC` 原因释放，
  不留下无所有者资源。
- 以上隔离只用于 synthetic 数据；未来真实数据必须共享现实状态，并依赖真实系统事务接口，
  没有事务接口时不得提供“真实预留”。

### 4.2 车主状态机

```text
IDLE
  → WAITING
  → SOFT_HELD
  → SESSION_RESERVED
  → NAVIGATING
  → OCCUPIED
  → DEPARTED

WAITING / SOFT_HELD / SESSION_RESERVED / NAVIGATING
  → CANCELLED / EXPIRED / FAILED
```

规则：

- `RECOMMENDED` 只存在于服务端原子事务内部；成功声明主车位后才返回 `SOFT_HELD`；
- `WAITING` 不持有车位；只有活跃客户端轮询、恢复连接或手动刷新才触发新推荐并开始软锁，
  后台事件不会为不可见用户提前启动倒计时；
- 纵深风险确认和普通位确认均发生在 30 秒软锁内；
- 备选是合规快照但不预锁；切换备选时，服务端原子地“尝试锁定备选，成功后释放原主位”；
  失败则保留仍有效的原锁或
  返回重新推荐，不产生两把锁；
- 确认后进入五分钟 `SESSION_RESERVED`，随后开始导航；
- 进入 `NAVIGATING` 不延长五分钟期限；超时释放车位、使路线失效并要求重新推荐；
- 推荐前检查预计到达时间加安全余量不超过预留窗口；动态重规划超出剩余期限时明确警告并
  允许用户重新推荐，不能静默续期；
- `OCCUPIED` 只有用户“已停入”或确定性测试事件才能产生；动画到达不产生占用；
- 关闭页面不释放占用；正常离场进入 `DEPARTED`；测试重置记录 `DEMO_RESET` 后释放；
- 所有命令携带幂等键，重试不能重复占位、重复释放或重复生成移位事务。
- 多标签共享匿名会话；命令携带期望状态版本，过期标签收到冲突并重新获取权威状态；
- 每次推荐/重规划使用独立 attempt ID；`FAILED`、`EXPIRED`、`CANCELLED` attempt 保持不可变，
  后续推荐创建新 attempt。

### 4.3 两套时钟

- 业务计时：服务端权威；单进程内以单调时钟计算持续时间，向前端返回 UTC 到期时间；若使用
  共享存储，则由存储 TTL 和原子操作控制，不受前端刷新、暂停或倍速影响；
- 仿真时钟：控制车辆移动和答辩演示，可暂停、单步和倍速；
- 答辩“60 秒预留”存在于隔离的 defense 场景配置，不改变 driver 场景的业务墙钟规则。

## 5. OnlineRuleServiceV2 的可实现定义

### 5.1 处理顺序

```text
校验 v2 请求和数据源健康
→ 限定停车场、会话和模式作用域
→ 将物理状态和全部有效 v2 声明投影到 v1 snapshot，布局结构保持完整
→ 调用 v1 只读适配器取得候选可行性与纵深恢复解释
→ 应用 v2 新硬约束（充电、营业、动态可达性）
→ 计算当前通道成本下的后端路线
→ 词典序排序并确定性平局
→ 原子创建主推荐软锁
→ v2 结果复核
→ 返回主推荐、至多一个合规备选、同源路线、解释和审计
```

不得先调用 v1 `decide()` 得到单一结果再暗中替换。适配器优先复用
`explain_arrival_candidates()` 的候选可行性、严格恢复判断和解释，再由 v2 层完成新增约束和
动态排序。不得通过预先删除非充电位等方式改变 v1 看到的布局容量或纵深结构；有效 v2 软锁、
预留、占用、关闭和异常必须在评估前投影，避免 v1 错估容量或恢复性。

### 5.2 排序口径

M2 必须用枚举和契约冻结排序，不使用无单位加权和。建议词典序：

1. 所有硬约束通过；
2. `strict_recoverable` 下新增不可恢复暴露为 0；
3. 新增被阻挡车辆数更少；
4. 剩余可分配容量更多；
5. 当前动态路线预计时间更短；
6. 距离更短；
7. 离场顺序不匹配更少；
8. 稳定 ID 平局。

若 M2 证据表明 v1 已冻结语义要求不同顺序，应记录变更并通过极小枚举例批准，不能静默调整。

### 5.3 结果身份

- 注册 ID：`online-rule-v2`；
- UI 名称：车主端“智能推荐”，答辩端“在线规则”；
- 审计同时记录 v2 服务版本、v1 适配版本、布局版本、动态成本版本和是否降级；
- v2 结果不得放入 v1 正式实验目录，也不得与 v1 指标直接比较。

## 6. v2 契约最小集合

M2 至少冻结以下资源及其 JSON Schema/OpenAPI 表达：

| 资源 | 最低内容 |
|---|---|
| ParkingLot | ID、名称、区域、synthetic 标识、营业、价格摘要、更新时间、数据源健康 |
| Layout | 版本、入口、节点、边、通道区、车位、纵深分组、缓冲位、坐标 |
| ParkingSpace | 作用域 ID、状态、充电能力、栈深、可分配原因 |
| DriverRequest | 会话、停车场、入口、充电硬条件、请求时间、幂等键 |
| Recommendation | 主位、合规备选、理由、路线、算法身份、求解/降级状态、软锁期限 |
| Journey | 预留、导航、占用、终止原因、当前合法操作 |
| Route | 节点/边、距离、动态预计时间、文字指引、成本版本 |
| SimulationEvent | 序号、仿真时间、墙钟时间、类型、主体、载荷、前后状态哈希 |
| AlgorithmDescriptor | ID、版本、类别、状态、输入要求、待接入理由 |
| DataSourceStatus | synthetic/real、健康、缺失字段、更新时间、失败关闭原因 |

所有时间注明时区或“仿真秒”，所有距离为米，价格明确只是参考值。真实适配器缺必填字段时
返回结构化错误；可以让用户显式切换 synthetic 场景，但不能混合补值。

## 7. 里程碑计划

### M1：视觉方向与高保真原型

前置：用户明确授权 M1 第一审批门。

第一审批门：

- 创建 M1 ExecPlan 和独立分支；
- 制作“城市智慧出行”和“未来停车舱”两套方向板；
- 两套均覆盖车主/答辩和电脑/手机核心片段；
- 生成 PNG，检查中文、层级、对比度、状态颜色和移动端密度；
- 停止等待用户选择。

第二审批门：

- 使用静态、明确标记的演示数据制作 HTML/CSS/JS 原型；
- 串联搜索、推荐、纵深确认、软锁、预留、导航、异常和答辩交互；
- 固定口令仅作视觉占位；原型不得被描述为安全实现；
- M1 只批准体验表现，不冻结算法、并发、安全或数据契约语义；
- 桌面至少验证 1440×900，手机至少验证 390×844，并补充窄屏 360px 检查；
- 用户批准后只冻结页面、流程、状态文案和首版功能边界。

退出条件：视觉与体验获批；未创建正式 React/FastAPI/v2 Schema。

### M2：契约、API 与在线规则 v2 服务

前置：M1 高保真原型获批。

- 建立 `schemas/v2/` 和 Schema 版本策略；
- 建立 FastAPI 应用骨架、配置、错误模型、健康检查和 OpenAPI；
- 建立 `SessionStore`、算法注册表和数据源适配接口；
- 建立 v1 只读适配边界与导入边界测试；
- 实现 `OnlineRuleServiceV2`、算法注册表和确定性解释；
- 实现纯 `RouteCostService`：读取版本化布局和给定成本快照，返回确定性路线与成本；M2 不负责
  生成实时通道事件；
- 实现四个版本化 synthetic 停车场的只读初始数据；
- 冻结 API 的资源语义，不冻结未来算法实现数量；
- 用极小人工例和两个固定成本快照验证普通位、纵深位、充电、无位、不可达、成本改变排序和
  显式降级。

退出条件：契约测试、OpenAPI 快照、v1 未修改检查和算法适配测试通过；用户批准 v2 契约。

### M3：共享状态机、路线和二维仿真核心

前置：M2 契约获批。

- 实现匿名会话、driver/defense 命名空间和场景克隆；
- 实现软锁、预留、导航、占用、离场、取消、过期、失败和重置状态机；
- 实现服务端墙钟、幂等命令和资源声明；
- 基于 M2 `RouteCostService` 实现转向文字；根据通道占用事件生成版本化动态成本快照并触发
  路线更新；
- 实现确定性事件日志和二维多车管理层仿真；
- 实现偏航、外部占位冲突、重规划、等待和纵深完整移位事件；
- 通过 API/测试客户端提供可运行的无 UI 演示，不等待前端才验证逻辑。

退出条件：状态转换表全覆盖，固定种子重放哈希一致，前端所需能力均可由 API 运行；用户批准
状态机和事件语义。

### M4：车主模式 React 前端

前置：M3 核心获批。

- 建立 React + TypeScript + Vite 和设计令牌；
- 实现找停车场、智能停车、当前行程三个页面；
- 四个停车场全部跑通推荐、预留、路线、异常和停车确认；
- 实现服务端倒计时同步、断线恢复、错误、空状态和显式降级；
- 车主端不出现算法名称、实验权重或技术下载；
- 电脑和手机使用同一能力矩阵，仅改变布局；
- 浏览器自动化覆盖主要流程，并人工检查 Edge/Chrome 与移动视口。
- 在进入 M5 前完成 M4 布局修订：保留 `Layout 2.0.0`/legacy 小场景，新增兼容的完整设施布局
  资源和四套大布局；实现共享 SVG 画布、只读布局预览和当前行程完整停车场；
- M4 只实现读取、预览和车主路线叠加，不实现布局导入、状态编辑、实验基线或答辩页面；
- 完整布局同时验证定向路网、纵深组、专用缓冲位、状态投影、缩放/拖动、手机全屏、轮询降级和
  Route 同源动画。
- M4 最终验收前增加 R5 确定性车主演示情景轮换：FastAPI 按匿名会话/停车场持有 profile，活动
  行程固定，空闲态可切换，终态后下一轮推进；React 只显示通俗 synthetic 状态，不复制 profile
  状态机或推荐逻辑；
- R5 只做 additive profile 摘要与切换命令，不实现 M5 的任意场景编辑、导入、实验基线或指标。
- 用户验收 R5 后另行批准受限 R6：仅把当前车主深层纵深离场的 blocker→buffer、目标→出口、
  blocker→原位规范事务接入共享画布；FastAPI 原子生成带 Route/哈希的权威 replay，React 只回放；
  通用多车运行器、播放控制、自由场景与完整纵深专题仍留在 M5。
- R6 用户验收前补充获批的 R6.1：推荐后由服务端形成本轮浅层 blocker，原子执行 blocker→buffer、
  当前车辆→深层位、blocker→原位并保存协调记录；后续离场复用同一 blocker。入位/离场仍是
  synthetic 当前车主的有限事件 replay，不扩展为 M5 通用多车仿真。

退出条件：普通用户可在电脑和手机查看完整布局并完成端到端停车流程；四套大布局真实通过推荐、
路线和状态恢复；无前端复制算法、几何映射或状态真值；用户重新验收 M4。

### M5：答辩模式与条件增强

前置：M4 车主端获批。

- 实现后端口令校验、短期答辩会话和路由保护；
- 实现项目总览、布局与状态、算法对比、交互仿真、纵深专题、研究证据、数据与扩展；
- 实现引导演示和自由实验台，共用 M3 事件引擎；
- 实现布局/状态/需求文件的校验、草稿/发布、场景副本、单个及批量状态编辑；
- 车主仍只使用 `OnlineRuleServiceV2`；答辩端在通过统一契约与公平性门后，可运行在线规则、
  最近可行和随机可行实验基线。其他待接入算法只显示元数据，不提供执行按钮或假结果；
- 实现单次对比、批量评估、固定种子、Pareto、用户权重和敏感性分析；
- 实现 JSON/CSV/HTML、浏览器打印 PDF、场景 PNG 和对比报告；
- 二维答辩功能在电脑和手机完整可用；
- 伪 3D 和声音仅在性能、稳定性和时间预算通过时加入，否则明确不实现且不影响验收。

退出条件：答辩模式权限、导入/发布、状态隔离、实验基线公平性、指标文档、失败案例、移动端二维
仿真和导出通过验收。

### M6：离线、公网与发布候选

前置：M1–M5 均获批。

- 移除所有运行时外部字体、图标或 CDN 依赖；
- 提供 Windows 一键启动、Docker、健康检查和清理方式；
- 生产式本地启动由 FastAPI 同源托管已构建前端，不要求终端用户安装 Node.js；
- 生成包含已构建前端和后端运行环境的离线发布物；在 M6 对“自包含可执行包”和“便携
  Python 3.11 环境”做最小兼容性比较后选择一种，验收机不依赖 Node、Docker 或联网下载；
- 本地启动时从环境读取答辩口令；缺失时生成临时口令并只输出到本地终端，不写仓库；
- 选择免费公网平台，部署单进程或提供与会话存储匹配的拓扑；公网强制 HTTPS；
- 配置 HTTPS、CORS、安全头、速率限制、日志脱敏和环境秘密；

## 9. 测试金字塔与质量门

- 静态：Python 类型/格式、TypeScript 严格类型、Schema 校验、导入边界；
- 单元：排序、过滤、状态转换、时钟、幂等、路线指令、数据适配；
- 契约：OpenAPI/JSON Schema、前后端生成类型或契约夹具；
- 性质测试：任一车位同一场景最多一个有效声明、状态不可逆跳转、释放后容量守恒；
- 集成：推荐到停车完成、充电等待、纵深拒绝、外部占位、断线重连、真实源失败；
- 重放：固定种子、事件序列和最终状态哈希一致；
- E2E：电脑/手机、车主/答辩、四停车场关键流程；
- 性能：API 决策预算、动画帧率、首屏资源和长时间仿真内存；具体阈值在对应 ExecPlan 中基于
  目标设备测定并冻结，不能结果出来后放宽；
- 安全：口令只在后端、无秘密入库、越权路由、输入边界、速率限制、日志脱敏；
- 交付：全新环境、断网、冷启动、服务重启、轮询降级和回滚。

任何失败都必须保留并说明；不得删除不利场景或把降级结果标成主算法成功。

## 10. 已解决冲突清单

| 原问题 | 唯一口径 |
|---|---|
| M3/M4 页面依赖原 M5 核心 | 共享状态机和二维仿真前移到 M3，页面在 M4/M5 |
| v1 冻结但要充电和动态路径 | `OnlineRuleServiceV2` 显式扩展，v1 只读 |
| 停车记录存在但演示释放占用 | 关闭页面不释放；正常离场或显式 `DEMO_RESET` 才释放 |
| 已预留车位又能“被占” | 定义为外部物理观测冲突，不是重复分配 |
| 固定原型口令与后端安全 | M1 仅视觉占位；正式版本后端环境口令 |
| M1 就冻结 `rc1` | M1 冻结体验边界，M2/M3 分别冻结契约/语义，M6 生成候选 |
| 双模式共享停车场又要求隔离 | 只共享 ID 和不可变布局，可变场景独立 |
| 答辩切换停车场可能影响车主活动状态 | 仅双方空闲时同步默认值，活动后各自固定 |
| 公网无账户却有预留状态 | 服务端匿名会话隔离，不提供跨设备持久化 |
| 答辩倍速与真实倒计时 | 业务墙钟和仿真时钟分离 |
| 答辩释放充电位却要求状态隔离 | 车主场景由自身调度器释放；答辩只演示独立副本 |
| 五分钟预留短于大型场景到达时间 | 推荐时校验 ETA 与余量，重规划超窗时警告或重新推荐 |
| 多标签可能创建多个行程 | 共享会话、状态版本和原子命令保证单活动行程 |
| 纵深普通备选与充电硬条件 | 备选必须同样满足硬条件，否则显示无合规备选 |
| 真实接口失败与离线模拟 | 真实源失败关闭；只能显式切换独立 synthetic 场景 |
| 伪 3D/声音与全端完整功能 | 二维全功能必过，二者是条件增强 |
| 回环 HTTP 与手机断网访问 | 电脑承担断网答辩；手机走公网实机验收，首版不开放明文 LAN |
| 一键离线但机器可能没有 Python/Node | 发布物包含后端环境和已构建前端，不依赖联网或 Node |
| 完整布局会破坏已批准小场景 | 新增兼容设施布局资源和大场景；`Layout 2.0.0`/legacy 保持可回归 |
| 车主只允许在线规则但答辩需要比较 | 车主仍只用在线规则；M5 验证通过的最近/随机方法仅作为实验基线 |
| PDF 报告与首版不引入重依赖 | 输出 JSON+HTML，使用浏览器打印样式另存 PDF，不做服务端 PDF |
