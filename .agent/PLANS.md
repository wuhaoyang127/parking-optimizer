# Codex 执行计划规范（ExecPlan）

本文件规定本项目复杂任务的计划格式。执行计划是可持续更新的设计与实施记录，不是一次性待办清单。

`PROJECT_STATUS.md` 负责项目级当前状态；ExecPlan 负责某一阶段或复杂任务的详细目标、里程碑、实施记录和局部决策。两者不得相互复制：ExecPlan 结束时只把项目级变化摘要同步到 `PROJECT_STATUS.md`，并在状态文件中链接当前计划或阶段交接摘要。

## 何时必须建立执行计划

满足任一条件时建立 `docs/plans/<阶段或功能>.md`：

- 跨三个及以上模块；
- 修改数学模型或数据含义；
- 引入新依赖；
- 预计超过一小时；
- 包含研究、原型、实现和验证多个环节；
- 失败可能破坏已有实验或结果。

## 执行计划必须自包含

读者只拿到当前仓库和该计划，也应理解：

- 要解决什么问题；
- 为什么要做；
- 当前状态是什么；
- 需要修改哪些文件；
- 如何判断完成；
- 如何恢复或继续。

不要依赖聊天记录中的隐含信息。

## 建议模板

```markdown
# <计划标题>

## 目标与用户可见结果
说明完成后用户能看到、运行或验证什么。

## 当前状态
列出相关文件、已有行为、已知缺陷和前置阶段结论。

## 范围
### 包含
### 不包含

## 关键定义与假设
列出数学、数据、时间单位、信息边界和业务假设。

## 里程碑
- [ ] M1 ...
- [ ] M2 ...

每个里程碑写明：
- 预计修改文件；
- 可观察结果；
- 验证命令；
- 停止条件。

## 详细实施步骤
用具体路径、类、函数和数据流描述，不写“完善代码”一类模糊句子。

## 验证与验收
包括单元测试、集成测试、极小人工例、性能限制和文档检查。

## 风险与降级
说明不可行、超时、数据不足、依赖安装失败时如何处理。

## 决策日志
- 日期：
- 决策：
- 备选：
- 理由：
- 证据：

## 进度记录
- 日期：
- 已完成：
- 实际验证：
- 问题：
- 下一步：

## 最终回顾
总结结果、偏离计划之处、未解决问题和后续阶段入口。
```

## 执行规则

- 开始实施前先完成计划的目标、范围、假设和验收部分。
- 每完成一个里程碑立即更新计划，不要最后补写。
- 发现原设计错误时先更新决策日志，再修改实现。
- 不隐瞒失败的尝试；保留简洁的原因与结论。
- 计划中的命令必须能从仓库根目录运行。
- 不把未经验证的未来工作写成已完成。
- 每个阶段最后停下等待用户验收，不自动进入下一阶段。


## 与项目状态的同步

- ExecPlan 创建后，由项目主线程把路径写入 `PROJECT_STATUS.md` 的 `current_exec_plan`；
- 每个里程碑更新 ExecPlan，不把全部过程复制到状态文件；
- 阶段结束时使用 `docs/handoffs/TEMPLATE.md` 创建交接摘要；
- 用户批准阶段后，再由主线程更新阶段状态、`latest_handoff` 和 `next_prompt`；
- 其他线程只能建议状态变化，不能直接提交 `PROJECT_STATUS.md`。
