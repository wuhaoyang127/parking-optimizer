# 灾难恢复手册（三把钥匙丢失场景）

> 用途：假设 Supabase service key、GitHub token、Render 账号三把钥匙全部丢失/泄露，如何恢复整个系统。

## 0. 结论先行

| 资产 | 丢失/泄露后果 | 能否恢复 | 靠什么 |
|---|---|---|---|
| 代码 | 被改/删 | ✅ 能 | GitHub 远程仓库（main / stage-d-deliver 均是最新） |
| 数据 | 被删/篡改 | ✅ 能 | 本地全量备份 `.redteam-backup-full-*.json` |
| 部署 | 被改/删 | ✅ 能 | 重新 clone + Render 重新部署 |

唯一前提：**备份文件不能丢**（见第 4 节，务必复制到云盘/U 盘）。

## 1. 三把钥匙清单与轮换

| 钥匙 | 用途 | 泄露后第一步 |
|---|---|---|
| Supabase service key（`sb_secret_...`） | 删/读全部数据 | Supabase 控制台 → Settings → API → 轮换 service key |
| GitHub token（`github_pat_...`） | 推代码 | GitHub → Settings → Developer settings → 撤销该 token |
| Render 账号 | 部署/改服务 | Render 登录页 → 找回/重置密码 |

## 2. 代码恢复

代码在 GitHub 远程，本地 token 丢了不影响：

```powershell
git clone https://github.com/wuhaoyang127/parking-optimizer.git
git checkout stage-d-deliver   # 或 main，两者当前同步
```

历史快照标签：`backup-before-pentest-20261121`、`v2.0-stable`。

## 3. 数据恢复（从本地备份）

备份文件：`.redteam-backup-full-<时间戳>.json`（含 9 张表全量，users 密码已脱敏）。

恢复方式：拿到新 service key 后，用 PostgREST 逐表 INSERT（`POST /rest/v1/<table>`），
关键表 `app_settings`（含 `driver_layouts` + `driver_release_store_state`）恢复后，
车主端重新部署即加载回所有推送布局。

> 已实测：删光 `app_settings` 后从备份恢复，10 个布局全部还原成功。

## 4. 你现在必须做的一件事

**把 `.redteam-backup-full-*.json` 复制一份到你的云盘 / U 盘 / 邮箱**。
因为这份备份目前只在本机，本机丢了就没备份了。这份文件含用户名等敏感数据，**别上传公开仓库**。

## 5. 部署恢复（Render）

1. Render 新建 Web Service → 连 GitHub 仓库；
2. 环境变量：`SUPABASE_URL`、`SUPABASE_ANON_KEY`、`SUPABASE_SERVICE_KEY`、`PARKING_PUBLISH_TOKEN`、`PARKING_ADMIN_TOKEN`；
3. 构建命令 / Dockerfile 已在 `driver/` 内，自动部署。

## 6. 研究端（Streamlit）

1. Streamlit Cloud 重新连 GitHub 仓库；
2. Secrets 配置 `[supabase]`（URL / anon key）与 `[driver_bridge]`（车主端地址 / 发布 token）；
3. 执行 `migrations/` 下尚未执行的 SQL（按编号）。

## 7. 防线结论（红队测试）

- 外部攻击（无钥匙）：SQL 注入、越权、暴力破解、数据直读、DoS 并发——全部被挡住；
- 唯一死穴：service key 泄露 → 可删库，但备份能恢复；
- 因此只要「钥匙不丢 + 备份在」，系统可随时重建。
