# 阶段 B 提示词：数学模型、伪代码与工程设计

当前阶段只把阶段 A 已批准的路线变成可实现规格。不要重新选择总体路线，也不要开始完整系统开发。

## 前置检查

1. 阅读 `AGENTS.md`、`PROJECT_STATUS.md`、`.agent/PLANS.md`；
2. 当状态指针不为 `null` 时，读取当前 ExecPlan 和阶段 A 交接摘要；
3. 阅读阶段 A 的全部批准输出，尤其是最终路线决策；
4. 确认阶段 A 已被用户批准；
5. 创建 `docs/plans/stage-b-specification.md`；
6. 先展示计划和待确认假设，再继续。

若阶段 A 未完成、未获批准或结论冲突，停止并报告。

## 任务一：严格定义问题

根据阶段 A 的批准路线，定义：

- 普通独立车位；
- 纵深车位组；
- 缓冲位；
- 入口、出口和路网；
- 车辆到达、预计离场、实际离场；
- 预约与非预约；
- 当前状态快照；
- 阶段 A 批准的决策触发、更新周期或规划范围；
- 已冻结决定和可调整决定；
- 阻挡、移位、等待、拒绝和出库延误。

若某概念不属于批准路线，应明确标注“不采用”并说明原因。所有时间、距离和利用率单位必须统一。

## 任务二：建立符号表和数学模型

至少给出：

- 集合；
- 参数；
- 决策变量；
- 辅助变量；
- 硬约束；
- 软约束；
- 分层目标；
- 与批准求解方法匹配的数学表达、逻辑表达或可计算评价方式；
- 求解状态、终止条件与降级条件。

必须区分：

1. 小规模离线全信息基准；
2. 在线即时策略；
3. 阶段 A 最终批准的动态决策方式；若未采用动态方法，明确说明。

如果采用 MILP、CP-SAT、动态规划、元启发式、匹配算法或其他方法，分别按其真实要求描述变量、可行性、邻域、线性化、整数化、终止和最优性含义，不得强行套用另一种求解器的术语。

纵深模型必须明确：

- `depth=1` 的物理含义；
- 何时产生阻挡；
- 一次移位如何计数；
- 移位目的地；
- 缓冲位容量；
- 离场顺序兼容条件；
- 未知离场时间的处理；
- 是否允许为了利用率主动接受未来移位。

优先设计可解释的目标优先级。若使用加权和，必须给出单位、归一化、权重来源和敏感性分析。

## 任务三：给出极小可验证例

至少设计三个可手工检查的实例：

1. 只有普通车位；
2. 两组二深纵深车位；
3. 有缓冲位和阻挡离场。

每个实例给出输入、可行方案、最优或已知最好方案、指标和验证理由。

允许在 `prototypes/` 中使用穷举、人工枚举或阶段 A 批准的求解工具编写极小验证脚本，但不得发展成完整系统，也不得把限时可行解写成已证明最优。

## 任务四：算法伪代码

给出：

- 路网或通行成本预处理；
- 阶段 A 批准的基线策略；
- 旧 Dijkstra-SA 对照的规范版本，仅在阶段 A 批准保留时提供；
- 阶段 A 批准的离线高质量基准；
- 阶段 A 批准的在线或动态核心方法；
- 超时、无解和缺数据降级；
- 纵深离场与移位执行；
- 事件日志与指标计算。

伪代码必须写清输入、输出、可见信息、状态修改、复杂度、终止条件和失败分支。

## 任务五：数据契约

设计 JSON/CSV/YAML 模式，至少覆盖：

- 路网节点和边；
- 入口出口；
- 车位和纵深关系；
- 缓冲位；
- 车辆；
- 场景；
- 算法配置；
- 事件日志；
- 指标结果。

明确哪些字段是：

- 实测；
- 用户输入；
- 仿真生成；
- 预测；
- 事后真值。

禁止在线或动态算法读取事后真值。

## 任务六：软件架构

给出最终目录、模块职责、核心类、函数签名、依赖方向和数据流。模块名称必须服务于阶段 A 批准路线，不强制保留无实际用途的模块。

通常需要覆盖：

```text
domain
io
network
demand
simulation_or_event_engine
policies
decision_or_optimization
evaluation
visualization
cli
```

可以根据批准路线调整名称，但必须解释。设计稳定接口，使阶段 D 的界面不复制算法逻辑。

## 任务七：测试和实验规范

设计：

- 单元测试；
- 集成测试；
- 人工可验证例；
- 信息泄漏测试；
- 可复现测试；
- 超时和降级测试；
- 指标边界测试；
- 低、中、高负载；
- 不同纵深深度和缓冲位；
- 预测误差实验，仅在采用预测模块时；
- 决策周期、规划范围或候选集实验，仅在批准方法包含这些机制时；
- 运行时间预算；
- 统计分析；
- 消融实验；
- 验收阈值。

不要预先承诺未知的提升百分比。

## 任务八：生成阶段 C 的正式输入

阶段 B 通过前，`prompts/C/` 下的文件只是通用模板。根据最终批准路线：

- 明确阶段 C 每个子阶段的真实技术名称；
- 标出哪些 C 提示词可以直接使用、哪些必须修改、重命名或删除；
- 生成 `docs/model/07_阶段C实现清单.md`；
- 不因为模板出现 SimPy、CP-SAT、滚动时域或其他工具名就默认采用；
- 用户批准阶段 B 后，才允许把通用模板转为正式执行提示词。

## 阶段 B 结束条件

- 数学定义无明显歧义；
- 极小例可验证；
- 每个目标能从标准日志或状态计算；
- 每个约束有明确实现位置；
- 信息边界明确；
- 求解术语与最终方法一致；
- 架构可逐模块实现；
- 正式实验协议已冻结；
- 已提出与实际结果一致的 `PROJECT_STATUS.md` 更新；
- 停止并等待用户批准，不开始阶段 C。
